# 动态恢复策略 v1.0

## 1. 策略清单

恢复策略不是"重启"的同义词。不同故障、不同资源条件需要不同动作，
本项目实现了 6 种可自动执行的策略（另有 2 种只读策略）：

| 策略 | 动作序列 | 前置条件 | 风险 | 典型场景 |
| --- | --- | --- | --- | --- |
| `restart_in_place` | 紧急保存 → 原地重启 | 有检查点 | 低 | 作业挂起、NCCL 超时、偶发 Xid 31 |
| `migrate` | 紧急保存 → 迁移 → 隔离卡 | 检查点 + 备机 | 中 | 单卡可疑（Xid 43/62/109、NVLink） |
| `evacuate` | 紧急保存 → 疏散 → 隔离节点 → 建单 | 检查点 + 备机 | 高 | 掉卡、不可纠正 ECC、PSU、节点宕机 |
| `shrink` | 紧急保存 → 缩容（去坏 rank） | 检查点 + world_size>1 | 中 | 慢节点无备机、反复坏卡 |
| `drain_restart` | 摘流 → 等待在途 → 重启 → 回填 | 健康检查可用 | 低 | 推理实例异常、p99 超 SLO |
| `degrade` | 降载（batch/并发） | 可调参数 | 低 | OOM、队列积压、过温、功率封顶 |
| `observe` | 只告警 | — | 低 | S3/S4、证据不足、观测不可信 |
| `fail_fast` | 升级人工 | — | 低 | 无检查点、无备机、重试耗尽 |

`shrink` 会改变全局 batch 与学习率，必须同步调整（线性缩放规则），
否则"恢复了但精度掉了"——这属于静默失败，比停机更难发现。

## 2. 决策表

决策输入：`Fault`（UFC 码 + 等级 + 范围）+ `JobContext`（检查点、备机、重试、
观测质量、慢节点根因）。决策顺序（先安全、后强度）：

```text
1. 观测质量 != OK            -> observe（记录 degraded_by_telemetry）
2. S4 / 观测类故障           -> observe
3. 推理服务                  -> drain_restart（崩溃循环 -> fail_fast）
4. 节点级致命码              -> evacuate；无备机/无检查点 -> fail_fast
5. 慢节点（UFC-JOB-007）     -> 按根因：
       hardware + 有备机     -> migrate
       hardware + 无备机     -> shrink
       load                  -> degrade（别换卡）
       unknown + 有备机      -> migrate 验证
       unknown + 无备机      -> observe
6. 作业级可恢复码            -> restart_in_place（重试耗尽 -> migrate -> shrink）
7. 卡级可疑码                -> migrate（无备机 -> restart -> shrink）
8. 容量类码                  -> degrade
9. 其余                      -> observe / 计划性处理
```

"节点级致命"清单（不允许原地重试）：`UFC-GPU-001`、`UFC-MEM-001`、`UFC-PWR-002`、
`UFC-NOD-001`、`UFC-NOD-004`、`UFC-DRV-001`。判据是：**故障可能损坏数据或让整机
不可用，重试只会放大损失**。

代码位置：`aiops/policy/engine.py`（决策） + `aiops/policy/strategies.py`（策略注册表）。

## 3. 升级阶梯

```text
observe -> restart_in_place -> migrate -> evacuate -> fail_fast
degrade -> observe（降载无效说明判断错了，回到观测）
shrink  -> observe
drain_restart -> fail_fast
```

触发升级的三个条件：

1. 动作后的验证失败（进度未推进 / 故障复发）；
2. 重试次数超过故障码的 `recurrence.max_retries`；
3. 同一对象在时间窗口内复发 `quarantine_after` 次。

升级不是"再试一次"，而是**换一个更强的假设**：从"进程问题"升级到"卡问题"，
再到"节点问题"，最后承认"自动处置解决不了"。

## 4. 检查点语义

恢复能力 = 检查点能力。没有检查点的"自动重启"只是把故障变成算力浪费。

### 4.1 三种保存

| 类型 | 触发 | 目标 | 代价 |
| --- | --- | --- | --- |
| 周期保存 | 时间（默认 300s）或步数（默认 200 步） | RPO 上界 | 周期抖动 |
| 紧急保存 | 故障信号 / 抢占 / SIGTERM | RPO≈0 | 停机时间 +`grace_s` |
| 手动保存 | 运维操作 | 里程碑 | — |

紧急保存有 `grace_s` 预算（默认 20–30s）；超时未完成就强杀，
用上一份周期检查点恢复（此时 RPO = 一个保存周期）。

### 4.2 存储要求

- **原子写**：先写临时目录，`fsync` 后 rename；中途掉电不会留下半份。
- **完整性**：`meta.json` 带 sha256，恢复前校验；校验失败按"没有检查点"处理。
- **保留**：最近 K 份（默认 3），避免磁盘被历史版本吃满。
- **兼容**：记录 `world_size`；缩容/扩缩后是否需要重分片必须显式判断，
  不能默认"能读就能用"。

### 4.3 RPO 度量

```text
RPO(有紧急保存)   = 失败步 - 紧急检查点步
RPO(仅周期保存)   = 失败步 - 最近周期检查点步
```

实验里这两个值的差就是"紧急保存"的价值：Xid 79 场景把 RPO 从 4 步降到 0 步
（见 docs/05）。

## 5. 幂等与防抖动

自动运维最危险的失败模式不是"没动作"，而是"动作风暴"。约束：

1. 同一 `(故障码, 对象)` 的冷却窗口内只动作一次；
2. 同一作业同一时刻只执行一个破坏性 Plan（最严重的那条）；
3. 迁移有"禁止回迁"标记，避免在坏节点和备机之间来回弹；
4. 缩容是单向的：不自动扩回，扩容走计划性操作；
5. 验证失败才升级，不允许"策略不变、参数微调"式重试。

## 6. 什么时候不该自动处置

以下情况必须交给人：

- 观测质量 `BLIND`（没有证据）；
- 厂商码置信度 `assumed` 且等级 S1（可能是误报）；
- 没有检查点且作业已运行超过 RPO 预算（重启=白跑）；
- 同一节点 24h 内第 2 次同类硬件故障（大概率不是偶发）；
- 动作需要带外权限（`fence_node`、换卡、改固件）。

## 7. 与调度器的边界

本项目只做"作业级"恢复，不做"重新排队/资源抢占"：

- 迁移 = 在已有备机池里换节点；备机不足时 `fail_fast` 并通知调度器；
- 缩容 = 改变作业的世界大小，需要框架支持弹性（torchrun elastic / DeepSpeed elastic）；
- 真正的重调度、排队、优先级抢占交给 Volcano/AIJob Operator，两边通过
  `quarantine_node` 标记与 `AIJob.status` 对接。
