### 2.1 真实 DDP 场景说明了什么

`11-torch-xid79` 不是仿真：两个真实 PyTorch 进程做 gloo all-reduce，
rank 1 被 `die.1` 杀掉，rank 0 随即卡在集合通信里。时间线：

```text
t+4.7s   检测到 Xid 79（事件驱动，不依赖 NCCL 超时）
t+4.7s   决策 evacuate；请求紧急保存
t+11.8s  强制清场（看门狗 + force_exit），落检查点 step 16
t+11.8s  迁移 localhost -> localhost-b，resume=True
t+19.2s  验证通过（step 24，故障未复发）
```

关键点：**靠 NCCL 默认超时（30 分钟）发现 rank 掉线是不可接受的**；
事件驱动检测把 MTTD 从分钟级压到亚秒级。这也是为什么要把 dmesg/Xid 纳入
检测链路，而不是只看框架指标。

### 2.2 "紧急保存"的量化价值

| 场景 | 仅周期检查点会丢 | 紧急保存后丢 | 收益 |
| --- | --- | --- | --- |
| 03 慢节点 | 2 步 | 0 步 | 100% |
| 04 ECC | 5 步 | 0 步 | 100% |
| 11 真实 DDP | 4 步 | 0 步 | 100% |

代价是停机时间里的保存窗口（`grace_s`）与一次额外写盘。在 4090 上单卡
70B 以下模型的检查点通常是秒级，这个交换是划算的；但**千亿参数模型必须用
异步/分片保存**，否则 `grace_s` 会盖不住。

## 3. 结论

1. **统一故障码是可行的，但要诚实标注置信度。** NVIDIA 侧 12 条码可以做到
   `verified`；AMD/昇腾目前是 `community`/`assumed`，只能用于只读告警。
   "跨厂商统一"不等于"已经拿到三家官方编码表"。
2. **事件驱动检测是 GPU 故障的关键路径。** 框架侧指标（步耗时、心跳）发现
   掉卡要等 NCCL 超时；dmesg 里的 Xid 能在亚秒级给出确定性证据。
3. **观测质量必须进入控制状态。** 实验中一旦心跳缺失，控制面会拒绝迁移；
   否则"看不见"会被误当成"没问题"。
4. **慢节点必须两路证据交叉。** 只用步耗时会把数据不均误判成硬件慢，
   导致无谓迁移；加上微基准后，`03` 场景才能正确选择"缩容"而不是"重启"。
5. **没有检查点就不该自动重启。** `05` 场景的 `fail_fast` 是特性不是缺陷：
   盲目重启会把"丢 5 步"变成"丢全部进度 + 浪费算力"。

## 4. 局限

- 规模：2 卡；MAD 稳健 z 分数在 n<5 时不可用，代码里已退化为比值判定，
  但大规模下的误报率还没数据。
- 时间：场景把阈值压到秒级（如挂起判定 300s→6s），生产阈值未在真实负载上校准。
- 硬件：没有 ECC/NVLink/HCCS/IB 的物理故障注入，相关路径只有回放证据。
- 恢复验证：只验证了"步数推进 + 故障不复发"，没有验证**训练精度是否等价**
  （需要固定随机种子、对比 loss 曲线，4090 上可做）。
- 策略：`migrate` 的备机选择是轮询，没有考虑拓扑（NVLink/IB 域）与碎片。

## 5. 4090 到货后的验证清单

| 优先级 | 实验 | 方法 | 通过标准 |
| --- | --- | --- | --- |
| P0 | 双卡 NCCL 基线 | `torchrun --nproc_per_node=2`，记录 step time 与 all-reduce 带宽 | 建立基线分布（median/MAD） |
| P0 | 慢节点识别 | `nvidia-smi -lgc 300,300` 锁一张卡频率 | 60s 内识别，策略选 shrink/migrate |
| P0 | 掉卡/驱动异常 | `rmmod nvidia` 或重启驱动（谨慎） | 事件驱动 <5s 检测，RPO=0 |
| P1 | 检查点开销 | 每 20 步保存，测保存耗时与训练抖动 | 保存 <2s，抖动 <5% |
| P1 | 真实故障码回填 | 触发/收集 Xid，核对 UFC 映射 | 每条 `verified` 都有日志证据 |
| P1 | AMD/昇腾真机 | `rocm-smi` / `npu-smi` 直连 | 采集器无需改代码即可产出统一指标 |
| P2 | DeepSpeed/Megatron | 用 7B 模型跑 ZeRO-2 / TP=2 | 重启后 loss 连续、无 NaN |
